# LinkedIn Jobs - парсер вакансий

*[English version](README.md)*

Django-админка + PostgreSQL в Docker. Собирает вакансии с публичных (гостевых)
страниц LinkedIn по поисковым запросам, хранит их вместе с профилями компаний
и выгружает в Excel/CSV.

## Запуск

Нужен только Docker Desktop. На чистой машине:

```powershell
.\build.ps1
```

```bash
./build.sh
```

Скрипт делает всё сам:

1. дожидается движка Docker (до 4 минут, если он ещё поднимается);
2. создаёт `.env` из `.env.example`, если его нет;
3. вычитывает базовые образы прямо из `Dockerfile` и `docker-compose.yml`
   и тянет их **с повторами** - сразу после старта Docker Desktop его внутренний
   прокси какое-то время таймаутит Docker Hub, и обычная сборка падает на шаге
   `load metadata for ...`;
4. собирает образ и поднимает оба контейнера, повторяя при сбое;
5. ждёт, пока админка ответит на `/healthz`.

Сам Docker скрипт не запускает - если движок не поднят, он подождёт и скажет об
этом. `build.ps1` работает и в `pwsh` на Linux, так что привязки к Windows нет.

| | |
|---|---|
| Админка | http://localhost:8000/admin/ |
| Логин | `admin` |
| Пароль | `admin` |

Логин и пароль задаются в `.env` (`DJANGO_SUPERUSER_USERNAME` / `DJANGO_SUPERUSER_PASSWORD`)
и создаются при первом старте. Чтобы сменить пароль уже созданного пользователя,
поставьте `DJANGO_SUPERUSER_FORCE_PASSWORD=1` и перезапустите.

Прочие режимы скрипта:

```powershell
.\build.ps1 -Logs      # логи
.\build.ps1 -Down      # остановить (база остаётся)
.\build.ps1 -Reset     # снести базу и начать с нуля
.\build.ps1 -Rebuild   # пересборка без кеша
```

## Что внутри

Два контейнера:

* `linkedin_jobs_web` - Django + gunicorn, собирается из `Dockerfile`
* `linkedin_jobs_db` - `postgres:16-alpine`, данные в томе `pgdata`

## Разделы админки

### Поисковые запросы

Что и где искать. Запросов можно завести сколько угодно - с разными странами,
ключевыми словами и фильтрами.

* **Страна** - все страны; LinkedIn резолвит локацию по названию, geoId не нужен.
* **geoId** - опциональное переопределение, если нужен конкретный город или регион.
* **Макс. запросов списка за запуск** - общий бюджет запросов к спискам на весь
  запуск, включая все задачи дробления. 1 запрос = 10 вакансий. **0 - без лимита.**
* **Таймаут** и **пауза между запросами** - настраиваются на каждый запрос отдельно.
* **Грузить описания / профили компаний** - отключаются, если нужен только быстрый список.
* **Макс. профилей компаний за запуск** - `0` без лимита. Страницы компаний LinkedIn
  лимитирует жёстче остальных и это самая медленная часть сбора; поставьте небольшое
  число, если вакансии нужнее. Названия и ссылки компаний собираются всегда - лимит
  касается только подробных профилей.

Кнопка **▶ Запустить** в строке запускает парсинг в фоне. То же самое доступно
групповым действием для нескольких запросов сразу.

Действие **⤓ Догрузить недостающие описания и компании** добирает всё, что
осталось после остановленного запуска, не обходя список заново.

Обработка идёт **постранично**: собрали страницу (10 карточек) → сразу догрузили
описания этих же вакансий → затем профили их компаний → и только потом пошли за
следующей страницей. Поэтому остановка в любой момент оставляет за собой
полностью обработанные страницы, а не гору вакансий без описаний.

Описания внутри страницы идут раньше компаний намеренно: это главные данные, а
job-эндпоинт почти не лимитируется, тогда как страницы компаний LinkedIn
придерживает регулярно.

### Вакансии

Собранные вакансии: название, компания, локация, «размещена повторно N назад»,
количество откликов, полное описание и **статус обработки**
(`Только из списка` → `Описание загружено` / `Ошибка загрузки`).

* Поиск по названию, компании, локации, **тексту описания** и job ID.
* Клик по названию компании в колонке «Компания» открывает **смежные вакансии**
  этой же компании; в карточке вакансии есть блок с профилем компании и ссылкой
  на все её вакансии.
* Фильтры: статус, наличие описания, повторная публикация, страна запроса,
  сам запрос, тип занятости, уровень, дата размещения.

Групповые действия:

* **⬇ Выгрузить в Excel (.xlsx)** и **⬇ Выгрузить в CSV** - 27 колонок, включая
  отрасль, размер, штаб-квартиру, сайт, число подписчиков и описание компании.
  CSV пишется в `utf-8-sig` с `;` - Excel открывает его двойным кликом без плясок.
* **↻ Повторно загрузить описания** - перезапуск для упавших записей.

### Задачи сбора

Обход потолка в 1000 результатов. LinkedIn отдаёт максимум 1000 результатов на
одну комбинацию параметров: `start=0..990` работает, `start=1000` отвечает
HTTP 400. Чтобы собрать больше, запрос дробится на подзадачи, и каждая получает
свою тысячу.

Задача - это одна комбинация фильтров. Дерево задач и есть «место, на котором
мы остановились»: статусы лежат в БД, поэтому остановка сохраняет фронтир, а
продолжение - это просто разбор очереди дальше.

Порядок осей дробления:

1. **По локации** - главная ось. Города берутся **из уже собранных вакансий этой
   же задачи**, а не из захардкоженного списка: LinkedIn резолвит строку локации,
   и тот формат, в котором он сам её отдаёт, гарантированно резолвится обратно.
2. **По дате** - `за месяц` → `за неделю` → `за сутки`. Окна вложенные, а не
   непересекающиеся (`f_TPR` это «за последние N секунд» от текущего момента),
   так что это способ добраться до свежего слоя, который в общей выдаче остался
   за тысячным результатом.
3. **По уточняющим словам** - из поля «Уточняющие слова для дробления»
   (`django, fastapi, senior`). Пусто - ось не используется.

Оси **не обязаны** быть непересекающимися: дедуп по `job_id` делает повторные
проходы безвредными, кривое деление стоит лишних запросов, но не ломает данные.

Колонка **«Пройдено страниц»** - это и позиция в выдаче: прерванная задача
продолжается с неё, а не с начала. Иначе задача с небольшим бюджетом вечно
перечитывала бы первые страницы и никогда не дошла бы до глубины. Действие
**↻ Вернуть в очередь** сбрасывает позицию в ноль.

В очереди первыми идут неисследованные задачи (позиция 0), и только потом
начатые - иначе корневая задача с её тысячей результатов съедала бы бюджет
каждого запуска, а подзадачи не получали бы очередь никогда.

### Компании и Запуски парсера

Справочные разделы: профили компаний (с числом вакансий и ссылкой на них) и
история запусков со счётчиками, логом и кнопкой **⏹ Остановить**.

## Как работает парсер

Только гостевые эндпоинты, **без кук аккаунта**:

```
/jobs-guest/jobs/api/seeMoreJobPostings/search   список карточек (10 шт. за запрос)
/jobs-guest/jobs/api/jobPosting/{job_id}         полное описание
/company/{slug}/                                 профиль компании (кэшируется в БД)
```

Это принципиально: автоматические запросы из-под залогиненного аккаунта
LinkedIn приводят к его блокировке, а гостевые страницы с профилем никак
не связаны.

* **Дедупликация** - по `job_id` (уникальный индекс). Повторная встреча вакансии
  обновляет запись и счётчик «раз встречена», а не плодит дубли. Компании
  дедуплицируются по slug, их профили грузятся один раз.
* **Остановка** - флаг в БД, который поток перечитывает перед каждым HTTP-запросом.
  Работает из любой вкладки и любого воркера gunicorn.
* **Ошибки** - повторы с экспоненциальным бэкоффом, отдельная обработка 429
  (с учётом `Retry-After`), 999 и 5xx. Одна битая карточка или страница не роняет
  запуск: ошибка пишется в лог и счётчик, работа продолжается. Запуск, прерванный
  перезапуском контейнера, помечается как прерванный и запускается заново.

### Ограничения LinkedIn

Проверено сравнением `job_id` в выдаче, а не предположено:

* **1000 результатов на комбинацию параметров.** `start=0..990` отдаёт данные,
  `start=1000` - HTTP 400. Обходится дроблением (см. «Задачи сбора»).
* **Работают только `location` и `f_TPR`.** Локация фильтрует по-настоящему:
  Киев и Харьков не пересекаются вообще. Дата публикации тоже работает.
* **`f_WT` (формат работы), `f_E` (уровень) и `f_JT` (тип занятости)
  игнорируются.** Гостевой эндпоинт принимает их молча и возвращает ровно ту же
  выдачу - пересечение 10 из 10 при любом значении. Поэтому в админке этих
  полей нет: делить по «ремоут / офис / гибрид» нечем.
* **Голое имя города резолвится не всегда**: `location=Lviv` отдаёт 0
  результатов, а `location=Lviv, Lviv, Ukraine` - полную страницу. Поэтому
  локации для дробления берутся из поля `location` собранных вакансий как есть.
* **Пустая страница не означает конец выдачи**: изредка приходит пустое тело
  (26 байт) в середине выдачи, а при повторе на том же смещении - все 10
  карточек. Поэтому пустая страница перепроверяется один раз.
* Паузу меньше 1 секунды ставить не стоит - прилетит 429.
* Страницы компаний лимитируются жёстче остальных: 999 прилетает регулярно.
* Автоматический доступ формально нарушает условия использования LinkedIn даже
  для публичных страниц. Для личного поиска и пет-проекта это обычная серая зона,
  для продукта нужен легальный источник данных.

## Консоль

```bash
docker compose exec web python manage.py run_search --list
docker compose exec web python manage.py run_search --id 1
docker compose exec web python manage.py run_search --id 1 --backfill
docker compose exec web python manage.py run_search --all-active
```

Последнее удобно повесить в cron или планировщик задач для ежедневного сбора -
вместе с фильтром «за сутки» потолок в 1000 результатов не достигается вообще.
